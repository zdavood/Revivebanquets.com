Revive website work is public-facing only. A separate agent owns VenueOS scheduling, inquiry processing, notifications, backend endpoints and data models. Preserve integration points and document required contracts rather than building a second CRM, form-storage system or scheduler.

**Why:** The owner explicitly divided these responsibilities in the marketing/conversion brief.

**How to apply:** Make safe frontend changes independently, but coordinate backend-dependent changes. Do not publish, change live domains or enable redirects without owner approval. Preserve authentic venue images and established gold/cream branding. Do not invent reviews, rental policies, inclusions or availability claims. Owner-confirmed seated capacity is up to 350 guests.

For VenueOS handoffs, never guess a tenant identifier or treat a generic calendar or HTTP 200 response as proof the integration works. Verify the public venue identity and distinguish unavailable configuration from unavailable dates.

**Why:** The owner's integration brief explains that missing tenant resolution previously appeared as “no openings,” and VenueOS development fixes may not yet be published.

**How to apply:** Keep production verification read-only: no test bookings, inquiries, customer emails or configuration changes. Check the hosted page identifies Revive and preserves the venue when switching options. Publication still requires separate approval.
